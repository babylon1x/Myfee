## 2. What MyFee is

- MyFee is a school fees portal for high-end private schools in Abuja.
- Schools pay for it. Parents use it free.
- The Owner sets fees once per class per term.
- Staff admit pupils and link each pupil to a parent.
- Parents see each child's fees and pay one fee for one child at a time, in full.
- Parents pay through Paystack or directly to the school. Paying through MyFee is optional.
- An assistant answers fee questions from this school's documents and this parent's own children's records only.
- MyFee never moves, holds or refunds money. Refunds happen in Paystack, outside MyFee code.

## 3. Terms

- **Required or Optional fee:** each fee is one of the two. Parents choose whether to pay Optional fees.
- **Online payment:** a payment made through Paystack checkout, including a transfer made inside checkout.
- **Offline payment:** cash, a teller or a transfer straight into the school's bank account, recorded by staff.
- **Reversal:** a new record that cancels a confirmed offline payment. The original payment stays visible.
- **Active link:** a parent-child link is active until staff remove it. Removed links are kept but give no access.
- **Code:** a one-time number sent by email to reset a password or approve a new staff or Owner device.
- **Lockout:** a block on login or codes for a set time after too many wrong tries.
- **Current task:** what I ask for in this session.

## 4. Users

| Role | Can do |
|---|---|
| Owner | Set classes, terms and fees. Add and disable staff. Give or remove the "can approve payments" permission. Approve offline payments the bursar recorded. See the security log. |
| Staff | Admit pupils, link parents, send invites, record offline payments, change a child's class. Cannot change fees. |
| Staff with "can approve payments" (the bursar) | Everything Staff can do, plus approve offline payments recorded by someone else. |
| Parent | See their own linked children, fees and receipts. Pay online. Ask the assistant. |
| Platform admin | Create a school and its first Owner by script. No screen in v1. |

- The Owner approves only offline payments the bursar recorded. The Owner cannot approve payments recorded by other staff.
- The last active staff member with "can approve payments" cannot be disabled or lose it until another active staff member holds it.
- Teachers, cleaners and other school workers get no accounts.
- Parents join by email invite only. Parents never link themselves to a child.

## 5. The one thing that must work

- A parent sees the correct fees for each child for the current term: what is paid, what is still owed, and when it is due.
- "Still owed" counts only unpaid Required fees. Optional fees are shown separately.
- A fee shows as paid only after Paystack confirms it to the server, or after a second person approves a recorded offline payment.
- Every paid fee gets a receipt.

## 10. Hard rules

### Money and payments
- Never mark a fee paid from the browser. Only the server marks a fee paid.
- Reject webhooks whose signature check fails. Call Paystack verify before opening a database transaction, never inside one.
- A verified Paystack success always confirms the payment, even if the attempt was marked failed or abandoned.
- Store money as `BigInt` kobo. Never use floats or 32-bit integers for money.
- Send amounts to the browser as strings of kobo. Format naira with the one shared helper (PRD Section 6.0).
- The server reads the amount from the stored fee. Never accept an amount from the client.
- One payment covers one fee for one child, in full.
- Hide Pay on paid fees and fees awaiting approval. If a payment for the fee has already started, ask the parent before starting another.
- A Paystack payment for a fee that is already paid is flagged for refund. Flag it only. Do not call any refund API.
- Offline payments: one person records, a different person approves. Nobody approves their own recording.
- If the bursar records an offline payment, the Owner approves it.
- A teller or transfer reference can back only one offline payment that is awaiting approval or confirmed.
- Never edit or delete a recorded payment. Fix mistakes with a reversal and a written reason.
- Write the audit log row in the same database transaction as the change it records.
- Only the Owner creates, changes or removes fees.
- Staff may change a child's class. A change that lowers a child's unpaid Required total goes to the Owner's review list.

### Data and access
- Always take `schoolId` from the session. Never from the request.
- Filter every query on school data by that `schoolId`.
- A parent sees a child's data only through an active link. Enforce this in the query.
- Check role and permission on the server in every page, server action and route handler. Middleware alone is not enough.
- Never delete rows, except document chunks replaced or removed by ingestion (PRD 9.4). Use the PRD's status fields to archive, remove, reverse or disable.
- Never add, rename or drop a table, column, index or constraint unless the current task names it. Change the schema only through Prisma migrations.
- Raw SQL lives in migrations. Write it only when the current task names the rule.

### Invites and accounts
- An invite link works once, expires after the time in the numbers table, and a resend cancels the old link.
- When a typed parent email matches an existing parent, show a confirm step naming that parent and their children. After linking, email that parent.
- Every user has their own login. Never build shared logins.
- Parents need no code on a new device. Staff and Owner do.
- Send every code to the account's own email. Codes go by email only.
- A new code cancels the old one.
- On a lockout, alert the email attached to that account.
- A successful password reset ends a login lockout and every other session.
- Reject passwords found in a known breach list.
- Take every limit, expiry and count from the decision log numbers table. Never type a number from memory.
- Until the config file for those numbers exists, stop and ask before writing code that needs a limit, expiry or count.

### Assistant
- The assistant reads only this school's documents and this parent's linked children's records.
- Questions about balances, due dates and paid status are answered with fixed text templates in code, filled from database queries. They never reach the model.
- Filter by school and family in the database query, not in the prompt.
- Embed only school documents, FAQs, policies and notices. Never embed anything about a family, payments, assistant messages or logs.
- The model gets no tools. The assistant route writes only its own log row.
- Assistant logs store IDs and statuses, never children's names.
- If it cannot answer from those sources, it sends the parent to the school.

### Interface
- No raw colours or sizes. Use design tokens only.
- Until the design token files exist, stop and ask before writing any styling.
- Red is only for real errors. Never use red for money owed.
- Test pages at phone width with the browser's "Slow 3G" throttle (FR-DASH-05).

### Secrets
- Never commit secrets.
- Never write a secret value into any file that Git tracks.
- Ask before creating any environment file.
